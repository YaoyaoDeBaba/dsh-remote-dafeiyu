## 二、这是设计缺口，不是偶发

转生的后半段**依赖"前世自己能写盘"**：

```
job 启动 → 注入"写交接文档"指令 → 等文件出现 → 建会话 → 投递首句
                                   ↑
                        这一步假设 agent 有写工具
```

而这条会话的工具被平台收走（只剩群消息/记忆/识图），于是整条链在最关键的一步断开，且**失败只是 job 状态变 failed**，用户看到的就是"停住了"。

## 三、修法（按优先级，建议全做）

1. **`handoff_rebirth` / `handoff_branch` 增加 `content` 参数**（最根本）：
   调用方把交接正文直接作为参数传进来，**插件负责落盘**——这样 agent 没有写盘工具也能转生。
   现状是"注入指令 → 等 agent 写文件"，把"能不能写盘"变成了转生的前置条件。
2. **超时兜底：仍然建会话**。等不到文档时不要只标 failed —— 用 `plan.note` + 「文档缺失，路径是 X，原因可能是工具被收走」拼一首句投给来生，让它自查补写。宁可来生多查一步，也不要整条线断掉。
3. **失败要显形**：超时的 message 里点名"可能工具被收走"，并在面板上红字提示 + 给一个「仍要建会话」的手动按钮。
4. **顺手修 job 不持久化**：`jobs` 是内存 Map，宿主重启后 `/handoff/status` 返回 `{"ok":true,"jobs":[]}`（本机实测）；重启前没等到文档的转生会被静默丢掉。建议落盘 `handoff/jobs.json` 并在启动时恢复 pending 的 job。
