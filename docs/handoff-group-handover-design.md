# 一键转生 · 群成员自动交接（方案稿，未实现）

> 提出：2026-11-20 · 状态：**待评审** · 关联：`handoff`（转生）、`groups`（拉群）、`.140`（preset 修复）

## 一、目标

一个在群里的会话执行转生时，**整条交接对群是可见、完整、可追溯的**：
先说"我要转生了"，转完把转世拉进群、把身份/群主一并交出去，最后说"后续由谁接手"。
用户不需要手动拉人、手动改名片、手动设群主。

## 二、流程（状态机）

```
转生开始
  └─ [S1] 群广播「我要转生」            ← 前置，必须有（否则群友一脸懵）
转生执行（前一版流程：写文档 / content 直写 / 超时兜底）
  └─ [S2] 新会话创建成功
  └─ [S3] 前世 ↔ 转世「互聊补缺口」     ← 有上限，见 §5
  └─ [S4] 重命名转世：<前世名>转世<N>
  └─ [S5] 拉转世入群 + 复制身份名角色（前世是群主则转移群主）
  └─ [S6] 群广播「交接完成，后续由 <新会话> 接手」
  └─ [S7] （待定）前世退役：移出群 / 标记 retired
```

每一步都要能独立失败，并且**失败要说出来**（群里 + 面板 + job.status），不许静默停住。

## 三、每条消息的文案（S1 / S6）

**S1 · 前世是普通群员 → 发给群主（定向）**
> 【转生预告 · 群名】
> 我的上下文已超载 → 将转生交接给下一世 → 稍后将我的转世拉进群。
> 交接期间我的群消息可能迟缓，急事请直接 @ 我（新的我）。

**S1 · 前世是群主 → 发给全员**
> 【转生预告 · 群名】
> 我要转生了（上下文超载）：先交交接文档，转世起来后我会把群主和身份一并交给他，
> 交接完成前这条群照常运作，分工照旧由我下。

**S6 · 前世是普通群员 → 发给群主**
> 【交接完成 · 群名】
> 已完成转世交接 → 后续我的工作由 `<新会话名>`（`<短号>`）接手。

**S6 · 前世是群主 → 发给全员**
> 【交接完成 · 群名】
> 已完成转世交接 → 后续我的工作由 `<新会话名>`（`<短号>`）接手，群主已一并转给他。

## 四、数据与接口（实现要点）

| 需要的东西 | 现状 | 要补 |
|---|---|---|
| 群归属 + 我的身份 | `groups.get(id)` 已有 members/role/owner | 前世启动时要能从 `sessionId` 反查所在群（目前只有群 id，没有反查） |
| 群发消息 | `groups.post({from, targets, kind})` 已有 | 转生流程里由**插件**代发（前世此刻可能没工具），文案走 `dispatchText` 同款 raw 投递 |
| 重命名会话 | `renameSession`（手机 `cmd.rename` 在用） | 转生 service 里调一次 |
| 拉人入群 | `groups.invite` 已有（会通知全员） | —— |
| 复制身份 | `groups.setMemberRole` 已有 | 前世 member.role 先读出来再写给转世 |
| 转移群主 | `groups.setOwner` 已有（仅用户侧可调） | 插件侧直接调服务，不走 HTTP |
| 序号 | 无 | `lineage.json` 里记 `parent → child`，序号 = 同一 base title 的已存在转世数 +1 |

**反查群归属**：新增 `groups.findByMember(sessionId)`（扫一遍群目录，成员表匹配）。
它同时是 S1/S6 的入口条件——不在任何群里就跳过整套流程。

## 五、"缺口清零"的判据（最容易失控的一步）

"让他俩聊到缺口清零"没有天然终点，必须有**硬上限 + 明确握手标记**：

1. 转世的首句里带 `群交接：<groupId>`，并要求它先读文档、把仍不清楚的点列出来（最多 3 条）；
2. 转世用 `handoff_ask`（已有的收件箱）问前世，前世答；
   - **这些问答默认只在两人之间**（定向），不进群——否则群里刷屏；
   - 群里只留 S1/S6 两条 + 一条系统记录「交接 Q&A N 轮」；
3. 转世回 `HANDOFF_GAPS_CLEARED`（或"无更多问题"）→ 判为清零；
4. **硬上限**：最多 3 轮问答、总时长 5 分钟；到点就带着剩余缺口继续（缺口写进 S6 的附注），绝不卡住；
5. 前世没有 `handoff_answer` 能力时（工具被收走）→ 直接跳到 S4，缺口写进 S6。

## 六、失败与幂等

- **S3 之前失败**（转生没起来）→ 群里补一句「转生没成功，我还在」，job 记 failed；
- **S5 拉人失败**（群满 12 人 / 会话不可用）→ 群里说清原因，并给出新会话短号，让用户手动拉；
- **群主转移失败** → 不静默：S6 文案改成"群主未转移成功，请手动设一下"；
- **宿主中途重启**：lineage.json 里记 `{child: {parent, groupId, stage}}`，启动时对 `stage < S6` 的做一次补偿（重试 S4-S6，只做未完成的）；
- 每个 stage 幂等：重命名看标题是否已带"转世"，拉人看成员是否已在群，群主看 owner 是否已是转世。

## 七、已定决策（2026-11-20 用户拍板：全部按建议）

1. **前世交接完成后移出群** ✅。理由：同一角色两个 agent 会让 @ 谁都能答、分工乱。
   代价：成员表里看不到"历史里那个说话的人"，但群记录与 lineage 都保留可追溯。
2. **序号按同一 base 累加** ✅：`2-3后端7 转世1`、`转世2`……
   前世本身已叫 `…转世N` 时，先剥掉 ` 转世K` 再 +1（即 `转世1` 的转世叫 `转世2`，不会叠成 `转世1转世1`）。
3. **群记录只留「交接 Q&A N 轮」+ 一句结论摘要** ✅，细节留在两人之间的定向对话里（不进群，避免刷屏）。

## 八、验收判据（先写，后实现）

1. 普通群员的转生：群主收到 S1，走完流程后群主收到 S6，且 S6 里的短号 == 新会话短号；
2. 群主的转生：全员收到 S1/S6，成员表里 owner 已换成转世，前世不再在成员表（若采纳 §7.1）；
3. 新会话标题 == `<前世名>转世<N>`，且 N 按 §7.2 规则；
4. 转世 member.role == 前世 role；
5. S3 超时/超轮时：流程仍然走完，S6 带"缺口未清零 N 条"；
6. 中途重启：lineage 里 stage 未完成的，重启后补完且不重复拉人/不改错名。
